# ADR-0097 — The event store's total order is a `sequence_no` column, not a timestamp

- **Status:** Accepted
- **Date:** 2026-08-26

## Context

`event_store` held two orders, and neither of them ordered the store.

`version` orders one stream. It is the aggregate's own count, so it says nothing about
how two streams interleave — which is correct, and is why per-stream rehydration was
never in doubt.

Nothing ordered the whole log. The primary key was a random UUID, which carries no
order. Both indexes — `uq_event_store_stream_version` and `ix_event_store_stream` —
were per-stream. That left two timestamp columns, and neither is a total order:

- **`occurred_at` is the domain moment, not the append moment,** and is not a total
  order even in principle. The profile-creating commit appends `PlayerProfileCreated`
  and `ProposalsOptInAnswered` with the *same* `occurred_at`, by construction
  ([ADR-0089](0089-player-profile-context-event-sourced.md)). It was also unindexed.
- **`created_at` is `func.now()`,** which in Postgres is *transaction start* time —
  identical for every event appended in one transaction, and not unique.

Two consequences, and the second is the one that decided this.

**Determinism, which is not a scale problem.**
[ADR-0093](0093-matcher-in-the-backend-with-a-pure-match-fit-engine.md) makes the
matcher's candidate index "a rebuildable projection — drop it and replay the event
store", and records that if the matcher and the backend disagree, the backend is right
and the matcher is rebuilt. That safety property assumes a replay produces the same
projection twice. Without a total order, two events appended in one transaction on
*different* streams have no defined relative order, so a rebuild may legitimately
differ run to run.

This was not purely prospective. `find_aggregate_ids_by_first_event` is a read *across*
streams, and it ordered by `(occurred_at, version)`. Its caller,
`_newest_open_by_sport`, scans the result in reverse to choose the run to resume —
so an undefined tie between two streams was an undefined answer to "which assessment
does this player resume?". The in-memory double returned true insertion order, so the
suite was asserting a guarantee the adapter did not give.

**Performance**, a distant second. Ordering a whole-store read meant a full scan plus an
external sort. Today that is nothing — a 50 000-player projection rebuild measured
~1.0 s — and it stays nothing for a long time.

**Why now.** The store is small and no environment exists past `local`
([ADR-0028](0028-four-environment-model-and-typed-configuration.md)), so this is one
migration against a near-empty table. Once the matcher's index, the outbox and the
outcome-join loop are all replaying, it becomes a table rewrite plus a backfill that
cannot invent an order for rows already written.

### Ruled out

- **Index `occurred_at` and order by it.** Cheaper, and wrong: it makes ties *fast*
  rather than making them *ordered*, and ADR-0089 guarantees the ties exist.
- **`(created_at, id)` as a composite order.** Deterministic, but not the append order —
  `id` is random, so it sorts events written in one transaction into an order unrelated
  to the order they were written in. A stable wrong answer is still wrong.
- **A `sequence_no` alongside the UUID primary key,** as first sketched. SQLAlchemy
  silently drops `Identity()` from a non-primary-key column on SQLite, leaving
  `INTEGER NOT NULL` with no default; every insert in the test suite — which runs on
  in-memory SQLite — would fail. Making the column the primary key is the shape both
  dialects generate natively.

## Decision

**We will give `event_store` a `sequence_no` column — a database-assigned, monotonic
append position — and make it the table's primary key. It is the store's only total
order, and the only column a read across streams may order by.**

- On PostgreSQL it is `BIGINT GENERATED BY DEFAULT AS IDENTITY`. On SQLite it is
  `INTEGER PRIMARY KEY`, that dialect's rowid alias and the only column it will
  auto-assign, declared as `BigInteger().with_variant(Integer, "sqlite")`. Widening the
  SQLite side to `BIGINT` breaks it silently — SQLite auto-assigns only a column spelled
  exactly `INTEGER PRIMARY KEY` — so the variant is load-bearing, not cosmetic.
- **The event's `id` stays, and stays unique.** It is the event's identity, carried in
  the outbox envelope. It simply stops being asked to imply an order it never had.
- **`occurred_at` keeps its meaning unchanged:** the domain moment. It is not a
  tie-break and must not be used as one.
- `find_aggregate_ids_by_first_event` orders by `sequence_no`, and that ordering is
  stated in the port's contract rather than left as an artefact of the query. The
  in-memory double models the same counter, so it can no longer pass on an ordering the
  adapter does not provide.
- **We will not add a whole-store replay reader yet.** Nothing replays across streams
  today; the column is what makes that reader cheap to add when the matcher's index
  needs one.

## Consequences

- A read across streams has a defined, reproducible order, so a projection rebuilt from
  the store is the same projection twice. ADR-0093's "drop it and replay" is a property
  the schema now supports rather than one it assumed.
- The resume path stops depending on a tie Postgres was free to break either way.
- Ordering a whole-store read becomes an index scan rather than a scan plus a sort.
  Irrelevant at today's size, which is the point of doing it at today's size.
- **The backfill cannot recover the true past order.** Existing rows are numbered by
  `(created_at, occurred_at, aggregate_type, aggregate_id, version)` — deterministic, so
  two runs agree, but an invention. That is exactly the cost this ADR is paying once to
  avoid paying later, and it is affordable only because only `local` exists.
- **A new write path must let the database assign the position.** Supplying
  `sequence_no` by hand — from application code, or from a data-loading script — puts
  a row at a position the identity counter will hand out again. The store is
  append-only and nothing does this today; the constraint is worth knowing before
  something tries.
- Postgres identity counters are not gap-free: a rolled-back transaction consumes
  numbers. `sequence_no` is an *order*, never a count, and nothing may read it as
  "how many events exist".
- One more column and one more index on the hottest write table. Both are small, and
  the index is the primary key that a UUID was occupying anyway.
