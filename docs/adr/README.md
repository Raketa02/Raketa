# Architecture Decision Records

Each ADR captures one significant architectural decision: the context and forces, the
decision, and its consequences. They are **immutable once accepted** — to change a
decision, add a new ADR that supersedes the old one. Don't rewrite history; the reason a
past decision looked right is itself information.

## Convention

- Files: `NNNN-short-kebab-title.md`, numbered sequentially from `0001`.
- Format: [Michael Nygard's template](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions) — see [`TEMPLATE.md`](TEMPLATE.md).
- Status: `Proposed` → `Accepted` → (`Superseded by ADR-XXXX` | `Deprecated`).
- **One sequence for the whole repo.** There are no per-app ADR directories: a decision
  that appears to affect one app usually constrains the others, and one numbered
  sequence is easier to reason about than two.

ADRs **0001–0004** were captured **retroactively** from the existing backend
implementation, so the baseline is documented. **0005–0009** are the decisions made when
the repo became a multi-app monorepo.

## The 2026-08-25 reset — why the sequence has gaps

The repository was deliberately reset to the three features that are finished end to end:
**sign-up, sign-in, and the onboarding questionnaire that produces a Skill rating.**
Everything built ahead of them was removed — the club console, the pairing and Match Fit
engines, and the unwritten Clubs / Courts / Matches / Money / Now contexts.

The ADRs that decided *only* removed things were removed with them, because an accepted
ADR describing code that does not exist is worse than no ADR: it reads as a constraint on
work in progress. The numbers are **not reused** — a gap is the record that something was
decided there and then taken out. Removed: **0007, 0011, 0014, 0016, 0023, 0025–0027,**
and **0030–0088**. The `docs/specs/now/` specification set went with them.

This is a reset, not a reversal. Nothing in the removed set was judged *wrong*; it was
judged premature. Anything rebuilt gets a fresh ADR at the next free number, argued from
the code that exists then.

## The 2026-10-06 Classic play removal — the second gap

On 2026-10-06 the older way of making a game was removed: *Classic play* — the Players deck and
its radar, the Chats tab, challenges with their where · day · hour plan, Find a game, the searches
behind them, the candidate index and the "who fits whom" ranking — together with the feature flag
that hid it ([PRD #569](https://github.com/Raketa02/Raketa/issues/569), tickets
[#572](https://github.com/Raketa02/Raketa/issues/572)–[#583](https://github.com/Raketa02/Raketa/issues/583)).
A group's Games deck and Fill in
([0189](0189-a-yes-books-a-court-and-the-club-is-the-seller.md)) are now the one way a game is
made.

**Unlike the reset, this is a reversal**: the loop was built and working, and the product owner
chose the Games deck as the one way to make a game. The convention above would supersede each
record with a new one; #569 ruled instead that **the old records are deleted, not superseded**,
and that a record half old and half live keeps its text and gains a dated note. That ruling is
this section's authority. The records that decided only that loop were removed for the reset's
reason: an accepted record describing code that does not exist reads as a constraint on work in
progress. The numbers are **not reused**. Removed: **0099–0101, 0104, 0109–0112, 0115, 0117, 0118, 0120–0123,
0125–0128, 0131, 0144, 0145, 0150, 0152, 0154, 0155, 0164–0166, 0168, 0173, 0177** and
**0180**, the feature-flag record. Its decision was **restated, not undeleted**, by
[0206](0206-a-feature-is-turned-on-by-a-pull-request-again-and-explore-is-the-first.md) on 2026-11-21, when the feature flags came back for Play's Explore. **0168** (*a member may leave the chat once the game is behind
them*) is among them for a second reason: it was only ever built on a branch that never merged, so
on this line it described code that never existed. The `docs/specs/the-loop/` set, the Play tab's
and the radar's specs and every matchmaking engine spec went too;
[`docs/specs/matchmaking/`](../specs/matchmaking/README.md) keeps only the copy deck, and says
where what is left of matchmaking is decided.

**A record that is half old and half live stayed**, with a dated *Note — the Classic play
removal* under its header naming what was removed and what still stands; the index below marks
each one. Some of the loop's own records are among them, because a live rule rests on them: the
cold-start location refresh (0174 §6), the gesture libraries (0176 §2), the Games deck's swipe
stage (0169 §3), the chat's grace (0151's rule), an event announcing only what the record cannot
reach (0142 §3), recomputing a pairing at read (0143), and no player calling a game off (0175). A link to a removed record is plain
text now — the number stays, so a reader can still find it in the history.

## When to write one

Write an ADR when a choice would be expensive to reverse, when you had to argue yourself
out of the obvious alternative, or when a future reader would otherwise assume the
current shape was accidental. Don't write one for a naming preference.

If your work **contradicts** an existing ADR, surface it rather than silently overriding:

> _Contradicts ADR-0006 (backend owns the contract) — but worth reopening because…_
